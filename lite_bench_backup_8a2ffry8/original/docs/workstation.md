# Kali Workstation runtime

The trusted runner and teacher browser stay in Docker on Ubuntu. Each attempt runs a disposable KVM Kali domain with one qcow2 overlay, libvirt NAT network, vsock CID, desktop, shell, PTYs, and CloakBrowser. The `kali-workstation` MCP controller and gateway persist outside the guest. The runner has neither the Docker nor libvirt socket.

The broker authenticates control requests with two independent generated credentials: an admin token used by the runner/host lifecycle and a controller token restricted to data-plane operations on an existing attempt. The App gateway uses a third independent App-control token. The broker records the exact task/attempt/environment/fingerprint identity in libvirt metadata, and places a per-attempt secret in a read-only ISO. It verifies the domain, network, overlay backing file, base digest, and guest agent before recovery. The agent accepts only host CID 2 over vsock and verifies every RPC. Guest root is untrusted.

The golden image lives at `/var/lib/libvirt/images/gpt-trace/kali-base.qcow2`. For each attempt the broker preallocates an ext4 loop image of `overlay_quota_gb` GiB and mounts it at `attempts/<identity-hash>/disk`; the overlay, identity ISO, and controller artifact store live inside. This reservation limits the amount of host disk an attempt can consume. `destroy` stops the domain, removes the network and nftables table, unmounts the disk, and removes the reservation. The ISO is mode `0600` and owned by the libvirt QEMU service account. Broker state containing its secret remains root-only.

The libvirt network supplies a guest DHCP lease and NAT. A project-owned nftables table for the attempt drops traffic to private, loopback, link-local, multicast, reserved, and IPv6 destinations. Guest traffic to the host is limited to the libvirt DNS and DHCP service. `egress_allow_cidrs` can explicitly allow a private target network after review; do not add Docker/control networks. The broker refuses a subnet that overlaps an existing host route. DNS/HTTPS egress is checked in `runner doctor`.

The persistent teacher browser uses pinned KasmVNC 1.5.0 as its X server and browser-native remote-control endpoint. KasmVNC listens only inside its container on TCP 6902 with HTTPS Basic Auth; the fixed internal username is `kasm_user` and its password is materialized from `TEACHER_BROWSER_PASSWORD` into a Docker file secret. A same-container HTTPS auth proxy listens on TCP 6901 and is the sole public-origin target. Anonymous top-level requests are redirected to an HTML password form rather than returning `WWW-Authenticate`; successful login creates a signed, eight-hour `Secure`, `HttpOnly`, `SameSite=Strict` cookie. The proxy forwards authenticated HTTP and WebSocket traffic to KasmVNC and injects the internal Basic credential, while a bounded in-memory failure window rate-limits password guessing. KasmVNC's own Basic auth remains enabled as defense in depth, but operators no longer depend on browser-native Basic Auth popups. Port 6901 is not published on the Ubuntu host. The `teacher-browser-tunnel` Compose service runs `cloudflare/cloudflared` on the shared `ui_egress` network and continues to connect to `https://teacher-browser:6901`, so existing remotely managed Cloudflare Tunnel routing does not need to change; keep `No TLS Verify` enabled because the proxy uses the same container-local self-signed certificate. The tunnel token is supplied by `TEACHER_BROWSER_TUNNEL_TOKEN`. The matching public HTTPS URL is deployment-local `TEACHER_BROWSER_PUBLIC_URL` in `.env`; Compose injects it into runner containers, so `make auth` never depends on the host's changing LAN/VPN address or hardcodes the hostname in versioned TOML. This infrastructure credential is independent of the Linux `browser` user and of the ChatGPT account/session. KasmVNC replaces the old Xvfb/x11vnc/websockify/noVNC chain; port 9222 remains loopback-only for host CDP diagnostics and the clipboard helper remains internal to Docker.

Browser interactions use the pinned CloakBrowser wrapper and its source-patched binary, installed into the image at build time. It runs headed on the same X11 desktop and uses an attempt-scoped fingerprint seed. Downloads go to `/home/kali/Downloads`, visible to shell. The separate teacher browser retains its own Docker volume and identity. `observe_screen` captures the libvirt display through `virsh screenshot` and returns it to the model as MCP `ImageContent` plus typed screenshot metadata; `computer_input` sends QMP key, tablet, button, and wheel events through the broker. These primitives remain usable when the guest agent or X11 input automation fails, provided QEMU's display and virtual input devices remain live. Text input uses the emulated US keyboard and GTK Unicode entry for non-ASCII characters; applications that do not implement that entry protocol need their own input method.

Initial workspace and attachments are seeded through a streamed tar archive. `export_file` copies a bounded file to the attempt's content-addressed broker store and returns `artifact_id`, size, and SHA-256 without placing the bytes in MCP JSON. `import_file` accepts a staged `artifact_id`; trusted clients stage and retrieve artifacts through authenticated `POST /control/artifacts` and `GET /control/artifacts/{artifact_id}` on the gateway. Broker-to-guest transfers use bounded 1 MiB vsock chunks and verify the complete digest. Artifact storage is removed with the attempt.

## Ubuntu host

Host-only Debian/Ubuntu packages are versioned in root `requirements.txt` and verified by `scripts/host_requirements.py`; the file is a system-package manifest, not a pip file. Docker Engine, Compose and Buildx are checked as host capabilities because their package names vary by installation source. Runtime hosts pull the prebuilt Kali golden from `aad7xppz4fd4r8emr/gpt-trace-kali-golden`; only the separate publishing machine needs the extra packages in `requirements-golden-build.txt`. `make build` performs the runtime preflight before creating the broker venv or Docker images. The broker process requires root for loop mounts and firewall rules, a libvirt system connection, a libvirt QEMU service user, and `/dev/kvm`. For VMware development, expose nested VT-x/AMD-V to Ubuntu; production uses bare metal KVM. Preserve the dedicated `/var/lib/libvirt/images/gpt-trace` storage root and the project state when recovering a running attempt.

Run `make build`, then `make up`, then `make doctor` on the configured host. `make doctor` first inspects host prerequisites and then runs the real PTY, Browser↔shell, screenshot, network, isolation and lifecycle smoke through the runner; it creates and destroys dedicated probe attempts. `make down` verifies ownership before removing project domains and networks. The broker is a privileged host process; use an appropriate root-managed service or invoke the project lifecycle with root privileges on a dedicated machine.

The Kali 2026.2 QEMU archive SHA-256 is pinned in the image builder. CloakBrowser wrapper `0.4.8` and free binary `146.0.7680.177.5` are pinned; the upstream binary download is signature-verified by the wrapper. Python dependencies are versioned with wheel hashes in `infra/workstation/image/requirements.lock` and installed with `--require-hashes`. `make publish-kali-golden` performs the existing real-KVM build once, verifies it, and publishes the four golden artifacts to Docker Hub under a tag derived from the full semantic build-input SHA-256. Runtime installation verifies that input fingerprint, the resulting qcow2 digest, the lock digest, and exact APT/Python package manifests before replacing the installed base. The APT `kali-last-snapshot` alias is still mutable: republishing after repository changes may produce a different qcow2 even for unchanged source code, so preserve the published image used by an experiment and review new provenance before replacing it.

The default attempt quota is 16 GiB, output buffer 1 MiB, screenshot 8 MiB, staged artifact 64 MiB, and seed archive 640 MiB. Limits are versioned in `config/runner.toml` and supplied to the broker, controller, and guest at creation. Image build and KVM/GUI/network isolation need validation on the actual Ubuntu host before SFT collection; unit tests in a non-KVM workspace cannot substitute for that gate.

## Manual ephemeral workstation

The Secure MCP Tunnel is persistent infrastructure; a Kali domain is not. Use `make tunnels` to ensure the OpenAI tunnel is running without creating a workstation. An already-running tunnel container is reused unless Compose detects effective configuration drift. The tunnel bootstrap validates tunnel-client liveness and an immediate read-only control-plane tunnel lookup rather than waiting for the normal 30-second command long-poll or requiring MCP `/readyz`, because the MCP backend is intentionally absent while no Kali runtime is attached. Use `make start_kali`, `make status_kali`, and `make stop_kali` for operator-driven work outside Superbench.

Manual mode uses the same `AppLifecycle` and `LibvirtWorkstationProvider` as benchmark attempts. The fixed logical task `__manual_kali__` gets a deterministic attempt identity, while `/data/state/manual-kali.json` records the exact task fingerprint and environment ID atomically. The runner state file is recovery metadata, not the sole source of truth: status also compares the gateway owner with broker-backed runtime discovery. If the gateway restarts while the VM survives, `stop_kali` can rediscover/rebind the recorded attempt and then run the normal reset/deactivate/destroy cleanup.

A manual state blocks benchmark/registration VM lifecycles, and `start_kali` refuses while an unfinished Superbench run or recovery journal exists. The gateway's existing single-owner `409` check remains a final defense against accidental overlap.
