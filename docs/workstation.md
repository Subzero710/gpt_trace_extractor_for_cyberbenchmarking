# Kali Workstation runtime

The trusted runner, ChatGPT teacher browser, PostgreSQL, MCP controller and gateway stay in Docker on the control host. The native broker and every Kali/evaluator VM run only on the execution host. Each attempt runs a disposable KVM Kali domain with one qcow2 overlay, libvirt NAT network, vsock CID, desktop, shell, PTYs, and CloakBrowser. The `kali-workstation` MCP controller and gateway persist outside the guest. The runner has neither the Docker nor libvirt socket.

The broker authenticates control requests with two independent generated credentials: an admin token used by the runner/host lifecycle and a controller token restricted to data-plane operations on an existing attempt. The App gateway uses a third independent App-control token. The broker records the exact task/attempt/environment/fingerprint identity in libvirt metadata, and places a per-attempt secret in a read-only ISO. It verifies the domain, network, overlay backing file, base digest, and guest agent before recovery. The agent accepts only host CID 2 over vsock and verifies every RPC. Guest root is untrusted.

The golden image lives at `/var/lib/libvirt/images/gpt-trace/kali-base.qcow2`. For each attempt the broker preallocates an ext4 loop image of `overlay_quota_gb` GiB and mounts it at `attempts/<identity-hash>/disk`; the overlay, identity ISO, and controller artifact store live inside. This reservation limits the amount of host disk an attempt can consume. `destroy` stops the domain, removes the network and nftables table, unmounts the disk, and removes the reservation. The ISO is mode `0600` and owned by the libvirt QEMU service account. Broker state containing its secret remains root-only.

The libvirt network supplies a guest DHCP lease and NAT. A project-owned nftables table for the attempt drops traffic to private, loopback, link-local, multicast, reserved, and IPv6 destinations. Guest traffic to the host is limited to the libvirt DNS and DHCP service. `egress_allow_cidrs` can explicitly allow a private target network after review; do not add Docker/control networks. The broker refuses a subnet that overlaps an existing host route. DNS/HTTPS egress is checked in `runner doctor`.

The persistent teacher browser uses pinned KasmVNC 1.5.0 as its X server and browser-native remote-control endpoint. KasmVNC listens only inside its container on TCP 6902 with HTTPS Basic Auth; the fixed internal username is `kasm_user` and its password is materialized from `TEACHER_BROWSER_PASSWORD` into a Docker file secret. A same-container HTTPS auth proxy listens on TCP 6901 and is the sole public-origin target. Anonymous top-level requests are redirected to an HTML password form rather than returning `WWW-Authenticate`; successful login creates a signed, eight-hour `Secure`, `HttpOnly`, `SameSite=Strict` cookie. The proxy forwards authenticated HTTP and WebSocket traffic to KasmVNC and injects the internal Basic credential, while a bounded in-memory failure window rate-limits password guessing. KasmVNC's own Basic auth remains enabled as defense in depth, but operators no longer depend on browser-native Basic Auth popups. Port 6901 is not published on the Ubuntu host. The `teacher-browser-tunnel` Compose service runs `cloudflare/cloudflared` on the shared `ui_egress` network and continues to connect to `https://teacher-browser:6901`, so existing remotely managed Cloudflare Tunnel routing does not need to change; keep `No TLS Verify` enabled because the proxy uses the same container-local self-signed certificate. The tunnel token is supplied by `TEACHER_BROWSER_TUNNEL_TOKEN`. The matching public HTTPS URL is deployment-local `TEACHER_BROWSER_PUBLIC_URL` in `.env`; Compose injects it into runner containers, so `make auth` never depends on the host's changing LAN/VPN address or hardcodes the hostname in versioned TOML. This infrastructure credential is independent of the Linux `browser` user and of the ChatGPT account/session. KasmVNC replaces the old Xvfb/x11vnc/websockify/noVNC chain; port 9222 remains loopback-only for host CDP diagnostics and the clipboard helper remains internal to Docker.

Browser interactions use the pinned CloakBrowser wrapper and its source-patched binary, installed into the image at build time. It runs headed on the same X11 desktop and uses an attempt-scoped fingerprint seed. Downloads go to `/home/kali/Downloads`, visible to shell. The separate teacher browser retains its own Docker volume and identity. `observe_screen` captures the libvirt display through `virsh screenshot` and returns it to the model as MCP `ImageContent` plus typed screenshot metadata; `computer_input` sends QMP key, tablet, button, and wheel events through the broker. These primitives remain usable when the guest agent or X11 input automation fails, provided QEMU's display and virtual input devices remain live. Text input uses the emulated US keyboard and GTK Unicode entry for non-ASCII characters; applications that do not implement that entry protocol need their own input method.

Initial workspace and attachments are seeded through a streamed tar archive. `export_file` copies a bounded file to the attempt's content-addressed broker store and returns `artifact_id`, size, and SHA-256 without placing the bytes in MCP JSON. `import_file` accepts a staged `artifact_id`; trusted clients stage and retrieve artifacts through authenticated `POST /control/artifacts` and `GET /control/artifacts/{artifact_id}` on the gateway. Broker-to-guest transfers use bounded 1 MiB vsock chunks and verify the complete digest. Artifact storage is removed with the attempt.

## Ubuntu host

The execution host host-only Debian/Ubuntu packages are versioned in root `requirements.txt`; control host uses `requirements-control.txt` without KVM packages. Both are verified by `scripts/host_requirements.py`; the file is a system-package manifest, not a pip file. Docker Engine, Compose and Buildx are checked as host capabilities because their package names vary by installation source. execution host builds its pinned Kali golden locally and requires the additional provisioning tools in `requirements-golden-build.txt`. All image files remain on its SSD. `make build` performs the runtime preflight before creating the broker venv or Docker images. The broker process requires root for loop mounts and firewall rules, a libvirt system connection, a libvirt QEMU service user, and `/dev/kvm`. For VMware development, expose nested VT-x/AMD-V to Ubuntu; production uses bare metal KVM. Preserve the dedicated `/var/lib/libvirt/images/gpt-trace` storage root and the project state when recovering a running attempt.

Run `make build`, then `make up`, then `make doctor` on the configured host. `make doctor` first inspects host prerequisites and then runs the real PTY, Browser↔shell, screenshot, network, isolation and lifecycle smoke through the runner; it creates and destroys dedicated probe attempts. `make down` verifies ownership before removing project domains and networks. The broker is a privileged host process; use an appropriate root-managed service or invoke the project lifecycle with root privileges on a dedicated machine.

The Kali 2026.2 QEMU archive SHA-256 is pinned in the image builder. CloakBrowser wrapper `0.4.8` and free binary `146.0.7680.177.5` are pinned; the upstream binary download is signature-verified by the wrapper. Python dependencies are versioned with wheel hashes in `infra/workstation/image/requirements.lock` and installed with `--require-hashes`. execution host `make build` provisions this pinned archive locally when the permanent golden is absent. Its atomic installation journal verifies all four artifacts, activates the independent QCOW2 last and preserves failed stages. Existing golden bytes are verified and never automatically replaced or removed. The APT `kali-last-snapshot` alias remains mutable; the stored image, resolved package inventories and complete actual provenance identify the experiment's permanent golden. No image upload, remote image registry or deployment-time prebuilt-image acquisition is part of this lifecycle.

The configured attempt quota is 64 GiB, output buffer 1 MiB, screenshot 8 MiB, staged artifact 64 MiB, and seed archive 640 MiB. Limits are versioned in `config/runner.toml` and supplied to the broker, controller, and guest at creation. KVM/GUI/network isolation and real ChatGPT/MCP operation need validation on both actual Ubuntu hosts before corpus collection; unit tests in a non-KVM workspace cannot substitute for that gate.

## Manual ephemeral workstation

The Secure MCP Tunnel is persistent infrastructure; a Kali domain is not. Use `make tunnels` to ensure the OpenAI tunnel is running without creating a workstation. An already-running tunnel container is reused unless Compose detects effective configuration drift. The tunnel bootstrap validates tunnel-client liveness and an immediate read-only control-plane tunnel lookup rather than waiting for the normal 30-second command long-poll or requiring MCP `/readyz`, because the MCP backend is intentionally absent while no Kali runtime is attached. Use `make start_kali`, `make status_kali`, and `make stop_kali` for operator-driven work outside Superbench.

Manual mode uses the same `AppLifecycle` and `LibvirtWorkstationProvider` as benchmark attempts. The fixed logical task `__manual_kali__` gets a deterministic attempt identity, while `/data/state/manual-kali.json` records the exact task fingerprint and environment ID atomically. The runner state file is recovery metadata, not the sole source of truth: status also compares the gateway owner with broker-backed runtime discovery. If the gateway restarts while the VM survives, `stop_kali` can rediscover/rebind the recorded attempt and then run the normal reset/deactivate/destroy cleanup.

A manual state blocks benchmark/registration VM lifecycles, and `start_kali` refuses while an unfinished Superbench run or recovery journal exists. The gateway's existing single-owner `409` check remains a final defense against accidental overlap.

## Trusted template artifacts and isolated evaluators

Template schema 2 verifies immutable root-owned generation manifests and their
resolved content identity, QCOW2 backing chains, source scopes, and opaque
artifact ID/hash/size mappings. The runner-only broker operation streams a
selected generation artifact to a fixed guest staging path with 1 MiB frames.
It accepts only the attempt's logical task and recorded generation, without
host-path input. Its size-bound guest session is independent of ordinary App
imports. Controller credentials cannot access template delivery or evaluator
operations; the model-facing tool manifest is unchanged.

An evaluator is a separate reserved overlay over the SAME immutable repo image
as its teacher attempt. It has a distinct vsock identity/secret/retry, no NIC,
shared writable mount, graphical console, App/gateway attachment or model route.
Guest evaluator identities reject browser, terminal and preparation RPCs. Hidden
test data goes only to this runtime; gold code patches go to neither runtime.

The broker records evaluator ownership before allocation, exposes diagnostic
inspect metadata, and preserves partial/stopped evaluators after technical
failure. Native pass/fail destroys the evaluator normally. Explicit resume may
abandon an old evaluator and must create a new one; reset-recovery abandons both
runtimes. A new verified registry activation never changes an existing attempt's
backing generation or selected artifact scope. Golden source inputs and guest RPC contracts are unchanged by this interface migration. Install the exact verified permanent golden matching the checkout.

## Separate physical hosts

[Distributed operations](distributed.md) put all App/control services on the control host and every VM, immutable template, artifact stage and evaluator on the execution host. Broker absence requires an authenticated resource audit; transport errors retain journals and never imply destruction. The MCP manifest and vsock guest contracts are unchanged.

The private broker transport uses a dedicated Cloudflare Tunnel to the native Unix socket and verified public HTTPS and independent admin/controller broker bearer authentication. the control host's Compose file is `compose.control.yaml`; neither runner nor controller mounts a host broker socket. Network failure preserves journals and does not prove absence. Runtime template selection verifies the root-owned local validation inventory, provenance and each used artifact; see [local template preparation](swe-gym-lite.md).

Global `make down` is coordinated on the control host. It first stops runner producers, drains new broker mutations, audits project ownership, destroys and proves absence of temporary execution host resources, acknowledges broker shutdown, and stops/removes only control host project containers/networks. It retains all persistent volumes, journals/checkpoints, native base/template images, source caches and unrelated resources. Invalid remote credentials or unreachable execution host still stop control host services and return an error for unconfirmed remote cleanup. An execution-host-local `make down` cannot stop the control services globally.


Finite preparations inherit a root-only cgroup v2 subtree of the existing `gpt-trace-distributed-broker.service` (`Delegate=yes`). Libguestfs uses its direct backend so detached helper processes remain inside this job's subtree. The durable job records this scope alongside PID/boot identity. Cleanup uses pidfds and, when required, the kernel subtree kill, then verifies the populated event and removes only the empty temporary scope. Source-fetch containers carry project, execution, preparation and attempt labels plus a fixed derived name; cleanup rechecks their identity, stops/removes only these temporary containers, and never prunes volumes or images. Unknown scopes, foreign container identities or unavailable inventory block a success claim. Fetch waits for the finite worker and its auxiliary resources to finish before reporting readiness.

The software tests use explicitly simulated cgroup control-file effects and Docker responses around real finite Python children, locks and immutable files. They do not exercise native cgroup, Docker, KVM, network listeners or physical benchmark integration. Native cgroup semantics follow the [Linux kernel interface](https://docs.kernel.org/admin-guide/cgroup-v2.html); delegation belongs to the [existing systemd unit](https://systemd.io/CGROUP_DELEGATION/).
